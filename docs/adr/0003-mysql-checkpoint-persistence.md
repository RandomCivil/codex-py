# MySQL-backed checkpoint persistence for resumable Agent runs

LangGraph Checkpoints for both the top-level Agent graph and each Step-execution graph will be stored in MySQL through the third-party `langgraph-checkpoint-mysql[aiomysql]` implementation, rather than a project-owned saver. The supported database contract is MySQL 8.0.19 through 9.5, verified by `agent migrate`. The current top-level Python loop becomes a state graph with plan, execute-step, replan, complete, and blocked nodes, checkpointed after each transition; it retains validated `AgentState` domain values behind an explicit serializable graph-state adapter. The CLI exposes `agent migrate`, `agent run --goal`, and `agent resume --run-id [--recovery retry|fail|abort]`; `run` and `resume` require `CODEX_MYSQL_URL` and refuse to migrate schema automatically. The CLI creates a UUIDv4 Agent-run ID for the top-level graph and derives Executor thread IDs as `{run_id}:r{revision}:s{step_id}`, so it can resume only the latest checkpoint without conflating a run with a user identity. A retry resumes the same derived Executor thread from its latest checkpoint. A project-owned `agent_runs` registry holds run identity, terminal status, non-secret configuration snapshot/fingerprint, and the execution lease, while the saver exclusively owns Checkpoint state. A 60-second database lease, renewed every 15 seconds against MySQL server time, permits only one active execution per run; an acquisition conflict returns `run busy`, and an expired lease permits a new resumer to mark the incomplete Step execution interrupted. The run and resume paths persist `pending → running` before an Executor invokes a model or tool. Checkpoint state is stored unredacted. If persistence is unavailable, the Agent fails closed before it can continue tool execution. Resume rejects a changed configuration fingerprint, while a completed or blocked run returns its prior terminal result without execution. Interrupted Step executions require an explicit recovery decision: retry only when every invoked MCP tool is explicitly host-registered as idempotent; an absent declaration is non-idempotent. Atom MCP currently declares no tools idempotent, so this release permits only failure-for-replanning or abort until that separate repository adds metadata. Signal-driven cancellation makes a time-bounded attempt to checkpoint the interruption and release its lease; expiry remains the hard-kill fallback. The checkpointer owns its schema through the explicit migration command, isolated in a dedicated MySQL database. Project-owned tables use versioned, idempotent migrations recorded before saver `.setup()` runs. CLI output is a stable one-line JSON record with documented exit codes: 0 completed, 1 blocked, 2 busy, 3 configuration, 4 persistence, and 5 invalid invocation. MySQL integration tests run against a locally available, dedicated `CODEX_TEST_MYSQL_URL` schema and never fall back to the runtime URL; they are marked `integration` and skipped when that variable is absent.

## Considered Options

- Implement a project-owned MySQL `BaseCheckpointSaver` — rejected because it would take ownership of LangGraph schema, serialization, pending writes, and compatibility behavior.
- Persist only the top-level Agent graph — rejected because a long-running Executor graph would still lose its in-step progress.
- Persist only the Executor graph — rejected because Plan revisions and serial step progress must also survive process loss.
- Automatically re-execute every interrupted Step execution — rejected because non-idempotent tool calls may have already produced external side effects.
