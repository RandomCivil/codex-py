# Asynchronous Observation generation with raw-evidence fallback

**Status: accepted.** This amends ADR-0010. Immediately after each Tool-call batch settles, the Runtime-context component starts one no-tool, strict-schema Observation request without delaying the ReAct or Plan-step Executor tool loop. There is no concurrency limit on those best-effort tasks. Every subsequent Runtime context is an instantaneous snapshot: its newest three Tool rounds are always complete Raw tool results; an older round contributes its validated Observation only when the asynchronous request has completed successfully, otherwise it contributes its Raw tool result. Thus, before the fifth Tool-round request, rounds 2–4 are raw and round 1 is an Observation if ready, otherwise raw. Observation request or validation failure is retained as diagnostic state and does not fail the active execution; it is not retried and the raw evidence remains authoritative fallback. A Raw fallback that, together with Durable State and required recent Raw results, cannot fit the context budget fails execution rather than being truncated or re-summarized. Budget-driven merging of already validated Observations remains synchronous because it is necessary to construct the next model request; a merge failure fails execution. When an execution becomes terminal, it neither cancels nor waits for outstanding Observation tasks, so they may still produce a result while the current process and event loop remain alive; they cannot alter the terminal Execution answer, and no persistent worker or cross-execution result handoff is introduced. This deliberate latency/evidence trade-off preserves uninterrupted tool use and never replaces evidence with an unverified summary.
