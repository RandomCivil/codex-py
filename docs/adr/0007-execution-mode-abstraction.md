# Execution-mode abstraction above the Plan-step Executor

**Status: accepted.** Whole-task execution is modeled as an Execution mode: `direct`, `tool_agent`, `react`, or `plan_execute`. An explicit mode factory selects a mode and each returns one Execution answer; a future deterministic router may compose the factory after task analysis, but task analysis and routing are outside this change. The existing `Executor` remains exclusively the Plan-step Executor inside `plan_execute`; it is not a common name or interface for the other modes. This preserves the audited Planner/Executor and recovery boundary while allowing simpler non-plan task paths without redefining their semantics. Only `plan_execute` participates in the existing durable run/recovery model; the other modes are ephemeral. A failed mode never escalates automatically. ReAct accepts completion only from a final structured `goal_satisfied` assertion, and `plan_execute` exposes its last successful Plan-step handoff without an additional model request. Tool-enabled ephemeral modes share one constrained Tool runtime per invocation. `tool_agent` executes only the first tool request from its sole model response and exposes that host-rendered result; later requests are ignored and traced; a tool or rendering failure is a failed answer. YAML gains `direct`, `tool_agent`, and `react` overrides alongside the existing components, each inheriting `model` defaults; the ReAct override alone requires Structured-output mode. YAML gains no CLI selector. Tool results are turned into answers by a shared deterministic renderer, not an additional model request.

## Considered Options

- Generalize the existing Executor to mean every execution path — rejected because it would silently invalidate its established one-Plan-step contract.
- Let task analysis choose a mode directly — deferred: task analysis is deliberately descriptive, and routing policy has not been designed in this change.
